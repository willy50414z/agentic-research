用工具將以下 YAML 寫入 `{OUTPUT_DIR}/checklist.yaml`：

```yaml
iteration: {ITERATION}

invariants:

  - class_name_unchanged
  - order_types_four_keys
  - no_lookahead_pattern

items:
  - id: M1
    type: param            # param | logic
    target:
      path: stoploss       # dotted path 進 config.json
    from: -0.05
    to: -0.03
    rationale: "OOS max_drawdown 0.31 超過 0.20 門檻"

  - id: M2
    type: param
    target:
      path: custom_params.max_units    # 策略自訂參數放 custom_params 子 dict
    from: 4
    to: 2
    rationale: "降低 pyramid 上限以收斂風險"

  - id: M3
    type: logic
    target:
      function: populate_indicators
    expected_signals:
      - "新 .py 中 populate_indicators 呼叫 ta.EMA 或等效實作，timeperiod 為 20"
      - "計算結果寫入 dataframe 的某個欄位（任意命名皆可）"
    forbidden_signals: []
    rationale: "加入趨勢過濾基礎"
```

# Schema 規則（嚴格遵守）

## 頂層必填

- `iteration`：當輪 analyze_attempt（整數）
- `based_on_intent`：固定為 `revision_intent.md`
- `created_by`：固定為 `llm2`
- `locked`：固定為 `true`
- `invariants`：必須完整列出 4 個，不可缺漏
- `items`：至少 1 項；每項都需要唯一 id

## items[*] 必填

- `id`：唯一識別碼，建議 `M1`、`M2`、`M3`...
- `type`：`param` 或 `logic`
- `rationale`：人類可讀的修訂理由（會被 audit 階段剝離後才給 LLM3，不影響審核獨立性）
- `target`：依 type 不同

## type=param 額外必填

- `target.path`：點分路徑，指向 `config.json` 內的單一欄位。
  - 例：`stoploss`, `max_open_trades`, `max_entry_position_adjustment` ← freqtrade 21 個內建可覆寫欄位
  - 例：`custom_params.max_units`, `custom_params.pyramid_step_atr` ← 策略自訂參數（baseline 策略以 `self.config.get("custom_params", {{}}).get(...)` 讀取）
  - 例：`minimal_roi` ← 整個 dict 替換（`to` 是新 dict 本身）
  - 例：`entry_pricing.price_side` ← 巢狀 freqtrade 欄位
- `from`：修訂前的值（型別與 config 中現值一致）
- `to`：修訂後的值（型別與 from 一致）

**禁止用 type=param 影響 hyperopt 搜尋空間**（low/high/categories）。本 revise 流程不調整 hyperopt 搜尋空間，僅調整 backtest 實際使用的參數值（從 config 讀）。

## type=logic 額外必填

- `target.function`：function 名稱
- `expected_signals`：至少 1 條；每條為**行為描述**，不可指定變數名或 syntax 細節
- `forbidden_signals`：可空陣列；若需要明確禁止某 pattern 才填入

## type=logic 可選

- `depends_on`：相依的 item id 陣列（純註記）

# Expected_signals 寫法（重要）

下游 LLM3 audit 看不到 intent.md 與 rationale，只靠 expected_signals 來判斷新 .py 是否符合預期。
所以這條規則的品質直接決定 audit 的可靠度。

✓ 好的 expected_signal（描述行為，給 LLM3 餘地）：
- "entry 條件含 close > 某 EMA-like column 的比較"
- "populate_indicators 函式呼叫 ta.EMA 或等效實作，timeperiod 為 20"
- "ta.ATR 不再被任何 entry/exit 條件引用"

✗ 太具體（卡死 subagent 的命名）：
- "出現 dataframe['close'] > dataframe['ema20']"
- "ema20 變數存在"

✗ 太抽象（LLM3 無法判斷）：
- "加上趨勢過濾"
- "改善訊號品質"
- "策略更穩健"

# 翻譯紀律

- intent.md 中提到的每條修訂方向，至少對應一個 checklist item（可拆成多個）
- intent.md 沒提到的東西，不可寫進 checklist（保持「契約」純度）
- 純參數調整（stoploss、minimal_roi、max_entry_position_adjustment、custom_params.* 等）一定走 `type: param`，不可寫成 logic
- 邏輯修改（新增/移除 indicator、修改 entry/exit 條件、新增自訂函式邏輯）一定走 `type: logic`
- 不要為了「看起來工整」把 logic items 強行套上 from/to 欄位

# 架構備忘（不影響你的輸出格式，但影響你的判斷）

下游處理：
- `type: param` 由 orchestrator 直接 patch 進 `config.json` 的 `target.path` 位置（不過 LLM、不動 `.py`）；
  freqtrade 載入時對 21 個內建欄位自動 override 策略 class default；
  策略自訂參數則由策略 `self.config.get("custom_params", {{}}).get(...)` 讀取。
- `type: logic` 由 subagent LLM 重寫策略 `.py` 中對應的 function body。

這代表：
- `target.path` 必須真的指向 config.json 的合法路徑（或 baseline 策略已宣告會從 `custom_params` 讀取的 key）。
- 改 `.py` 中的 class attribute 是**未授權變更**，會被 audit 抓——所以 param items 一律走 config 路徑。
